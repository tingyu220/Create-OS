结论：实际输出表现为保留原稿后又续写约 4500 字。证据支持“续写指令 + 未说明已有正文长度/新增预算”造成模型误解；不能证明模型内部推理。统计口径始终是非空白字符（含标题、标点），并非中文词数算法不一致。

生产任务、候选、会话、工作稿仅做文件读取，没有实例化生产 Runtime、重跑真实模型或写入上述文件。核查前后对候选、会话、工作稿及正式稿存在状态做 SHA256 比较：4 项全部一致，正式稿仍不存在。

## 最小设计与实施

1. 先用 Fake Client 捕获实际模型请求，覆盖空稿、1200 字、4700 字、6045 字输入及候选/基线继续修改。
2. 新增纯计算字数契约助手，由现有 Runtime 调用；不建立另一条模型执行流程。
3. 字数目标明确为最终完整章节总量，不是新增字数。输入长度来自本次 Proposal 冻结输入，不能只看正式稿，也不读取后续变化的工作稿推测预算。
4. 若保留既有内容，剩余目标预算为 `max(0, target-input)`，新增上限预算为 `max(0, max-input)`。已有正文超上限时，明确整合、压缩原内容；续写和改写均输出一章完整候选，不能原文照抄后再新增一章篇幅。
5. 保持软约束：不截断输出、不拒绝保存、不自动重试。统计报告随任务及候选持久保存，旧记录不回填。
6. 明确报告整章实际总量、输入量、净变化及范围。只有已超用户范围且高于目标 1.5 倍或低于目标 0.5 倍时标为“显著偏离”；这是提示阈值，不是质量或保存门禁。
7. 显著偏离仍保留候选，作者可自行接受，也可在既有“继续修改”入口选择候选/原稿并明确压缩或补足目标范围，确认后才会执行。界面显示最终整章目标及显著偏离提示。
